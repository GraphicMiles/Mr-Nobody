### A. Read-loop economics — the owner's six rules

Core principle wired in: *cheapest sufficient action first; escalate only on
validated failure, never preemptively.*

1. **Evidence-sufficiency early exit** — new `EvidenceSufficiency` (planner):
   after each read, if ≥2 distinct (body-deduped) sources each contribute ≥2
   question-matching prose sentences (reusing `ExtractiveAnswer.pick`, post
   boilerplate/prose gates, cross-source sentence dedupe), the remaining read
   steps are skipped without being fetched. Device evidence: "whats the time"
   53s/5 pages, "how old is messi" >69s/6 pages, both user-stopped.
2. **Escalate only on validated failure** — `readBestEffort` now refuses to
   launch the headless browser when the read could not be recorded anyway
   (read cap hit, duplicate URL, evidence already sufficient) — that was the
   "browser after a successful 3.0s http.fetch" screenshot. Escalation still
   happens when http output fails `ReadableText.usable()` / the contract, or
   the host is a known challenge/SPA. Escalated page loads are capped at
   **8s** (`BROWSER_FETCH_TIMEOUT_MS`), passed to `browser.fetch`/`links`.
3. **ClockSkill** — time/date/day questions answer from the device clock,
   zero network, before classification or planning. Handles "in <city>" by
   IANA-zone resolution; unresolvable places fall through to research rather
   than guessing a timezone. Hooked in `DeterministicEngine.run` right after
   the direct-reply path.
4. **No retry on success-but-imperfect** — `FetchRetry.MAX_ATTEMPTS` 3 → 2
   (one retry, hard failures 429/502/503 only, as before). The pngtree
   "2.1s then 20.2s recovered" pattern is killed by rule 2's guards.
5. **TaskBudget** — new wall-clock ceiling (`agent/policy/TaskBudget`):
   90s research / 120s download, checked between steps on both the
   deterministic and autonomous paths and inside the download link harvest.
   On expiry the engine composes the answer from evidence in hand (snippets
   at worst) — never a spinner death.
6. **Cheap-success ranking** — `SiteMemory` gains a clamped ±3 per-host
   http-outcome score (recorded by `HttpTool` on every fetch: usable text vs
   failure/needsBrowser); new `CandidateRank.byCheapSuccess` stable-sorts the
   CHOOSE PAGES candidates by it in `planReads`.

### Harness 1 — Tool scope (`ToolScope` + `callScoped`)

research = search/http/browser (+download only on download intent; terminal

`callScoped` seam every run-path call goes through; the autonomous planner

stays unscoped by design, and scope is cleared at run start.

### Harness 3 — Outcome check (`OutcomeCheck`)

download says so in as many words; a named site answered entirely from

## 2026-08-21 (later) — DEFECT: crash on first Nobody toggle (embedded Tor)

**Report:** owner screenshot — "Mr Nobody closed because this app has a bug"
immediately on enabling Nobody mode, APK 20914b8, no Orbot installed.

**Root cause (confirmed from sources, not guessed):** tor-android's POM
declares ZERO dependencies. TorService.onCreate's first statement calls
androidx LocalBroadcastManager, which therefore was not in the APK →
NoClassDefFoundError on the main thread → process death. The crash happened
inside the service lifecycle, past any try/catch in EmbeddedTor.

**Fix (three layers):**
1. Package `androidx.localbroadcastmanager:localbroadcastmanager:1.1.0`
   explicitly (the actual repair).
2. `EmbeddedTor.isBundled()` now also verifies LocalBroadcastManager is on
   the classpath — a future build that loses the dep refuses Nobody honestly
   (Orbot-only message) instead of crashing.
3. `isBundled()` uses non-initializing Class.forName so the availability
   check no longer triggers TorService's static `System.loadLibrary("tor")`.

Wiring tests pin all three. JVM suite green at 879.

**Fix journey to green:** f0430d6 (the fix) → b907773 (sandbox had stripped
the exec bit off tools/*.sh; restored — recurring environment gotcha, watch
for it in every commit) → 5340051 (bundled-check test made environment-aware:
Gradle's unit-test classpath HAS the AAR, the javac harness does not; the
non-initializing Class.forName is also what keeps Gradle unit tests from
loading libtor). Flutter Build ✅ + Emulator Smoke API 31/34 ✅ at 5340051.
JVM suite 881 green. Owner retest: T1/T2 (crash is prevented by packaging
LocalBroadcastManager; verify Nobody now applies and exits via Tor).

## 2026-08-21 (later still) — DEFECT 2: release-only crash in the tor thread

**Report:** owner stack trace — NoSuchFieldError: no "J" field
"torConfiguration" in TorService, thrown from mainConfigurationFree (native),
frames showing R8-obfuscated names (TorService.i, inner class $c).

**Root cause:** release builds minify with R8; libtor.so resolves
TorService's fields via JNI (GetFieldID) at RUNTIME, invisible to R8, which
stripped the private fields. The 0.4.7.14 AAR ships no consumer proguard
rules. Debug builds don't minify — hence green CI emulators alongside a
crashing release APK. Lesson recorded: for JNI-heavy deps, emulator-green ≠
release-green; the smoke tests exercise debug.

**Fix:** app-level proguard-rules.pro keeping org.torproject.jni.** and
net.freehaven.tor.control.**, applied via proguardFile on the release build
type (appended to Flutter's own rules). Wiring test pins the rules AND that
the file is actually referenced. JVM suite 881 green.

## 2026-08-21 — UX: bundled Tor auto-applies (owner picked option A)

Why the wait exists at all (physics, not implementation): a cold Tor start
must download and verify the relay consensus and build a 3-hop circuit;
10-60s on mobile data, same as Orbot. It is a first-start cost — the
service stays warm afterwards and caches the consensus on disk.

What changed: toggling Nobody while the bundled Tor bootstraps no longer
refuses with "try again". The core reports pending (fail-closed, nothing
routed yet), a generation-guarded background waiter holds the request open
for the real budget (BOOTSTRAP_WAIT_MS=90s), and applies the mode itself at
the first circuit, persisting the achieved mode. Any newer user decision
(switching to NORMAL mid-bootstrap) supersedes the waiter. Async failures
surface exactly once via the new privacyStatus channel method. Dart:
setPrivacyMode shows "Starting built-in Tor — Nobody switches on when it
connects", polls privacyStatus (2s interval, bounded at 60 polls), and the
mode label flips by itself. JVM suite 884 green.

## 2026-08-21 — Bug 10 (THE Tor bug): the availability probe lied on the main thread

Owner ⓘ after fresh install: refusal pair with NO waiter breadcrumbs — the
waiter succeeded and the post-bootstrap re-apply still refused. Root cause:
route.isAvailable()'s socket probe, when called from the mode toggle (a
main-thread platform-channel call), hits Android's NetworkOnMainThread
policy; the catch treated that exception as "not listening". A running,
ready Tor was therefore refused at the final gate on every MANUAL toggle —
while the suite, running on an executor thread, probed fine. This single
defect explains the entire family of "refused with [tor status=ON]"
device results.

Fix: the probe detects the main looper and runs the connect on a
short-lived worker (bounded by the same timeout); plain JVM tests probe
directly. The background waiter now always logs its outcome (up/status/
elapsed) so no verdict is ever silent again.

JVM suite 911 green.

## 2026-08-22 — Tier 0 execution safety: durable identity before design tools

The agent harness now distinguishes a reusable task row from one execution
cycle. Every new task/follow-up/recurring wake receives a durable run ID;
retries keep it. Tool operations combine task + run + logical step + effect
slot + an argument fingerprint into a deterministic idempotency key.

A separate SQLite execution ledger is now the recovery authority. It stores
step/effect state, bounded replay results, external references, and reserved /
actual cost fields. On retry, committed calls replay without execution. Reads
may be repeated; idempotent adapters receive the same key; an ambiguous
non-idempotent effect fails closed instead of being guessed or repeated.
Remote AI calls use the same ledger boundary, and remote-worker submission
persists/reuses its remote task ID.

Task submission now has an atomic client-key + short-window fingerprint dedup
path. Startup re-enqueues durable QUEUED rows, closing the insert-before-
WorkManager crash gap. Agent downloads persist the harness key in their own
store so a retry returns the original transfer instead of creating a second
file.

Generic async infrastructure landed separately from any design vendor:
AsyncJobAdapter, durable job store, and coordinator for submit, poll,
reconcile, terminal result, external reference, and cost. No Canva/Figma
adapter or credential is present.

Verification: full JVM suite 987 green; privacy-auditor suite 13 green;
repository privacy audit clean. Flutter tooling was unavailable locally, so
strict Dart analysis/widget tests remain for CI.

## 2026-08-22 — Provider resilience, two lanes, design sessions, and official Canva MCP

The post-Tier-0 stack now pins AI provider/model/base and execution platform
per run. Explicitly consented remote fallback providers are frozen with that
run; if every remote provider fails, evidence already gathered is completed by
the deterministic local extractor without replaying a tool effect. Failures
share one typed taxonomy and bounded retry policy. Mutable scope, tool
snapshots, repeat/work guards, browser anchors and provider choice moved into
AgentRunContext, allowing two fair local execution lanes.

A top-level SkillRegistry now routes clock, design and research before the
search-specific router. Design work uses a durable parent session across
bounded turns, with independent safety, creative-review and finalization
gates. Candidate selection, revision state, export state and idempotency-aware
per-session quotas are persisted. A fake platform adapter proves the full
draft → reject/revise → approve → export state machine without a network.

The production design adapter uses Canva's official remote MCP endpoint over
Streamable HTTP. It discovers tools dynamically, grants only the scoped Canva
operations, supports generation/candidate selection, conservative exact-text
editing transactions, commit, and export. Canva does not document effect
idempotency, so ambiguous mutations stop rather than retry. Candidate
thumbnails are immediately captured as bounded local previews; signed export
URLs are consumed by the app-owned downloader and scrubbed after completion.

Canva authentication is per-user OAuth 2.1 authorization code + PKCE. Access,
refresh and pending-state values use Keystore-backed EncryptedPreferences and
never enter model prompts or MCP arguments. The OAuth callback is consumed by
the native core before ordinary deep-link routing. Live connection is
fail-closed until a build supplies a Canva-approved HTTPS CIMD client URL and
allowlisted redirect URI.

Generic external jobs now have a WorkManager poll lane, adapter registry,
startup rescheduling, cancellation, and a WAITING_EXTERNAL task state. This is
the transport-neutral seam a future persistent remote worker/server will use
for hour/day-long work.

Verification: full JVM suite 1,028 green; privacy-auditor suite 14 green;
repository privacy audit clean; strict Flutter analysis clean; all 167 Flutter
widget/golden tests pass locally with the four intentional classic/warm S6
golden updates. PR #1 and the merged-main signed-APK workflow are green. Live
Canva/device evidence remains pending until an approved CIMD/redirect exists.

## 2026-08-22 — Batch: server-backed update notifications (metadata-only)

**Scope (owner-approved):** the update-notification system from the brief —
quiet startup check, Settings badge, cached/offline behavior, dismissal,
metadata-only contract. Landing page and `website/update.json` schema had
already landed; the app side and the service were not started.

### What shipped

1. **Update service (`server/`)** — zero-dependency Python stdlib service,
   deployable to Render via the included blueprint (`render.yaml`).
   Serves the landing page, `/update.json` (the app's endpoint,
   `Cache-Control: no-cache`), `/health`, and the other `website/` statics.
   Path traversal rejected; every mutating method refused; 1 MiB body cap.
   `website/update.json` is the single source of truth for both the
   landing page's metadata card and the app.
2. **Release helper (`tools/publish_update.py`)** — validates the version,
   computes the APK sha256, stamps publishedAt, rewrites
   `website/update.json`. Refuses non-https URLs and malformed versions.
   Signing metadata stays a documented placeholder until apksigner digests
   are settled.
3. **Java core (`browser/update/`)** — `UpdateInfo` (paranoid payload
   parsing: semver, https-only download URL, well-formed checksums — a
   placeholder sha256 is rejected, not displayed), `UpdateStatus` (pure
   status computation, no Android imports), `UpdateChecker` (NetworkGate
   round-trip with 5 s/6 s timeouts, 64 KB cap, last-successful-check
   caching, per-version dismissal). Three new MethodChannel methods:
   `updateStatus` (instant, offline-safe), `updateCheck` (one quiet
   round-trip on the existing single-thread executor; failure returns the
   cache flagged `networkFailed`), `updateDismiss`.
4. **Flutter** — `UpdateStatus` model in `AppState`; the quiet kickoff
   check runs once per session from `load()` and is never on the critical
   path; a stale (>6 h) check is repeated when the app resumes.
   Settings gained an "App" section: an Updates row with a badge (accent
   dot for optional, warning dot + persistent banner for required — nudge
   only, the app never blocks), and a detail sheet with version,
   optional/required chip, release notes, publish/check times, truncated
   sha256, "Update" (hands the download URL to the app's browser; the
   install stays Android's signed job) and "Remind me later".
5. **Docs** — README "Updates" section + "Update distribution" under
   what-is-not-finished; ROADMAP built-list, Priority 3 "Updates
   distribution" work, and the startup-request exception noted.

### Why it is built this way

The brief's security constraint is the shape of the system: the server is
metadata, not code. There is no auto-download, no silent install, and
nothing that could execute remote bytes. The check goes through
`NetworkGate`, so in Nobody mode it rides the same privacy route as
everything else and fails closed with the route. "Required" is a
persistent nudge, not a gate: a plain signed APK outside the Play Store
cannot be force-installed, and locking users out would break the product.

### How it is proven

- JVM: 18 new tests — `UpdateInfoTest` (parsing, https enforcement,
  placeholder-sha rejection, numeric version ordering incl. 1.10.0 > 1.9.9)
  and `UpdateStatusTest` (badge, dismissal for-that-version-only,
  offline fallback, malformed cache). Ran green locally against the same
  junit/json versions as the gradle build.
- Server: run locally and probed — health, update.json (body + no-cache),
  landing page, HEAD (headers, no body), traversal (raw + encoded), POST/
  PUT/DELETE refusal, 404. `tools/publish_update.py` verified: sha256
  matches `sha256sum`, bad version and http URL refused, `--required`
  honored.
- Flutter: `app/test/updates_settings_test.dart` pins the channel contract
  (badge appears only for a newer non-dismissed version; dismiss calls the
  core with exactly that version and clears the badge; up-to-date and
  never-checked states). Runs in CI with the rest of the Flutter suite.
