3 · Entry B — tapped from Tasks Same screen, scrolled to the end. Traces collapse to one line each so the thread stays readable across many runs. Every answer carries its read time, and the figure check appears inline where the claim is.

The one thing that isn't free

Streaming does not exist yet. AiProvider.complete() hands back one finished string, and both remote providers read the whole body before returning (while ((line = r.readLine()) != null) sb.append(line)). The caret in screen 2 is a real design, not a real capability.

Making it true means adding a token callback to the provider interface, requesting stream:true, parsing server-sent events, and forwarding chunks over an EventChannel rather than a one-shot MethodChannel reply. That is a contained change, but it is a change to the AI layer and the bridge, not to the UI — worth knowing before it is treated as a styling task.

The trace can stream today. It comes from TaskEventStore, which is append-only with a contiguous per-task sequence and is already written as the agent works. Polling it every ~400ms gives a live pipeline with no backend change. So screen 2 splits cleanly: trace now, token stream after the provider work.

What each piece is made of

  • Mark, not a bubble — the existing BrandLogo painter, at 26px. Bubbles on the agent side would cap a long answer at ~80% width and make citations and warnings look like chat rather than findings.
  • Thinking line — the current step from step.changed, so it names the page being read rather than saying "Thinking…". A generic spinner is indistinguishable from a hang.
  • Trace rows — tool.call, tool.result, tool.denied. Timings are the durations the pipeline already records.
  • Stop button — cancelTask exists on the channel and is wired.
  • Amber note — FigureCheck, added this session.

Still to decide

  • Address bar disambiguation. Drawn as ↑ for ask, ⏎ for search. Needs testing — it is the one place a wrong guess wastes the user's request.
  • How many runs post a message. Two shown. At 24 a day this needs collapsing; suggestion is one message only when something the user asked about changes, with silent runs folded into the trace line.
  • Approval inline — a tool needing confirmation should ask as a message with two buttons, not a modal that can be dismissed and lost.
